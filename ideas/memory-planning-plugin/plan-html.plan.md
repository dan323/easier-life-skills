# memplan — `.plan.md` HTML Rendering Format

## Goal

Every `.plan.md` file produced by `memplan-cli.js render` must follow a Markdown
structure that converts to well-formed, styled HTML without any manual cleanup.
The rule is: **the `.plan.md` format is the source of truth for both the plain-text
human view and the HTML rendered view** — the same file serves both.

A companion `memplan-cli.js html` command (see `scripting-layer.plan.md`) converts
any `.plan.md` (or all of them) to a `.plan.html` file with embedded CSS.

---

## Markdown constraints that make HTML rendering clean

Every `.plan.md` file must follow these structural rules (enforced by the canonical
render algorithm in `memplan-cli.js`):

### Heading hierarchy

| Level | Used for |
|-------|----------|
| `#` (H1) | File title only — always the first non-comment line |
| `##` (H2) | Top-level sections (e.g. `## Steps`, `## Risk`, `## Open Questions`) |
| `###` (H3) | Sub-sections within a section (rare; only when a section has named groups) |

No `####` or deeper. No heading-skipping (e.g. H1 → H3).

### Section order

Each file type has a fixed section order (declared in the renderer schema in
`scripting-layer.plan.md`). This is not just for determinism — it ensures the HTML
page always has the same visual layout for the same file type, regardless of when it
was last updated.

### Status badges

Step status is rendered inline as a bracketed tag immediately after the step text.
The tag must match one of the canonical values so the HTML converter can apply
colour classes:

| Badge text | CSS class | Colour |
|------------|-----------|--------|
| `[done]` | `.badge-done` | green |
| `[in-progress]` | `.badge-in-progress` | blue |
| `[blocked]` | `.badge-blocked` | red |
| `[skipped]` | `.badge-skipped` | grey |
| `[pending]` | `.badge-pending` | no colour (default) |

Example rendered step line:
```markdown
1. Implement FeedScript parser [in-progress]
   1.1. Write tokeniser [done]
   1.2. Write op-dispatcher [pending]
```

The HTML converter replaces `[<status>]` with `<span class="badge badge-<status>">…</span>`.

### Key-value pairs

Mutable keys are rendered as a definition list (`<dl>`) in HTML. In Markdown they
are rendered as a two-column table with `Key` / `Value` headers — no prose wrapping,
one row per key:

```markdown
| Key | Value |
|-----|-------|
| last-action | Updated checkpoint.mem with parse result |
| next-action | Run inbox processor against testdata |
| open-questions | — |
```

The HTML converter applies `<dt>`/`<dd>` pairs styled as a compact property grid.
Empty values are shown as `—` (em dash) — never omitted in the HTML view, unlike
the Markdown view where they are suppressed.

### Append-only entries

Append-only entries (facts, failures, questions, entities) are rendered as a
`<table>` with `Timestamp | Key | Value` columns. In Markdown they appear as the same
table structure:

```markdown
| Timestamp | Entry | Value |
|-----------|-------|-------|
| 2026-05-20T14:31Z | fact | auth-middleware uses JWT HS256 |
| 2026-05-21T09:12Z | fact | no mock DBs — real DB only per persona |
```

Timestamps link to nothing; they are just a stable sort key visible to the reader.

### Risk and warning callouts

`risk.plan.md` sections render as blockquotes in Markdown so they visually stand out
even in plain Markdown viewers. The HTML converter maps blockquotes to styled
`<aside class="callout callout-risk">` elements:

```markdown
> **What could break**: auth middleware swap touches every request path — regression risk
> **Irreversible**: once old middleware is deleted, rollback requires a new deploy
> **Verify first**: run integration test suite against staging before merging
```

### Questions section

`memory/questions.plan.md` (and the `open-questions` field in `checkpoint.plan.md`)
highlights unanswered questions with a `⚠` prefix in Markdown. The HTML converter
wraps them in `<aside class="callout callout-question">`:

```markdown
⚠ Is the plannotator `.feedback` schema final, or will it gain new ops?
⚠ Should `budget.mem` include indirect dependencies or only direct ones?
```

## Example: `plan.plan.md`

```markdown
<!-- GENERATED by memplan — do not edit directly. Send feedback via .memplan/inbox/ -->

# Plan

| Key | Value |
|-----|-------|
| title | Implement FeedScript inbox processor |
| step-count | 12 |
| current | 4 |
| status | in-progress |

## Steps

1. Scaffold `.memplan/` directory [done]
2. Write MemScript tokeniser [done]
3. Write MemScript renderer [done]
4. Implement `inbox` command in memplan-cli.js [in-progress]
   4.1. Parse FeedScript header [done]
   4.2. Dispatch each op type [in-progress]
   4.3. Delete `.feedback` on success [pending]
5. Write unit tests for FeedScript ops [pending]
…
```

In the HTML view this renders as:
- A compact property grid at the top (`title`, `step-count`, `current`, `status`)
- A numbered list with colour-coded status badges
- Sub-steps indented under their parent

## HTML page structure (produced by `memplan-cli.js html`)

Each `.plan.html` file is a self-contained, single-file HTML document with embedded
CSS. No external dependencies. Structure:

```html
<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <title>{file-title} — memplan</title>
  <style>/* embedded, see below */</style>
</head>
<body>
  <header class="mp-header">
    <span class="mp-file-name">{filename}.plan.md</span>
    <span class="mp-generated">Generated {ISO8601 timestamp}</span>
    <a class="mp-index-link" href="index.html">← All plans</a>
  </header>
  <main class="mp-content">
    {rendered sections}
  </main>
  <footer class="mp-footer">
    Generated by memplan — edit via .memplan/inbox/
  </footer>
</body>
</html>
```

### Embedded CSS palette

| Token | Value | Used for |
|-------|-------|----------|
| `--mp-bg` | `#f9fafb` | page background |
| `--mp-surface` | `#ffffff` | card/section background |
| `--mp-border` | `#e5e7eb` | borders |
| `--mp-text` | `#111827` | primary text |
| `--mp-muted` | `#6b7280` | timestamps, generated labels |
| `--mp-done` | `#16a34a` | done badge |
| `--mp-progress` | `#2563eb` | in-progress badge |
| `--mp-blocked` | `#dc2626` | blocked badge |
| `--mp-skipped` | `#9ca3af` | skipped badge |
| `--mp-risk-bg` | `#fef9c3` | risk callout background |
| `--mp-risk-border` | `#ca8a04` | risk callout border |
| `--mp-question-bg` | `#fff7ed` | question callout background |
| `--mp-question-border` | `#ea580c` | question callout border |

Font: system-ui stack — no web font fetch. Max content width: 800px centred.

### `index.html` (generated alongside the per-file pages)

When `html` is run on a directory, it also writes `.memplan/index.html` — a dashboard
listing every `.plan.md` with its status badge (extracted from the `status` key) and
the `next-action` or `title` as a subtitle. This is the entry point for a human
browsing the `.memplan/` directory.

---

## What the HTML converter does NOT do

- It does not call out to any CDN or external resource.
- It does not parse or render the `.mem` files — only `.plan.md`.
- It does not watch for changes — it is a one-shot command. Pair with a file-watcher
  or a `memplan/record` step if live preview is wanted.
- It does not write inside the agent's read-only `.plan.md` files — output is a
  separate `.plan.html` sibling (or a separate `html/` subdirectory — see the
  `html` command spec in `scripting-layer.plan.md`).
